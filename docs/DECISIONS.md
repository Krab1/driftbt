# Decisions

Append-only. Format: `D-n В· date В· decision вЂ” why вЂ” consequence`.

- **D-1 В· 2026-10-13 В· Use `librqbit` as the engine, no own protocol implementation** вЂ” mature, async, DHT/magnet/PEX/UPnP/IPv6/streaming/limits included; writing a client engine from scratch is weeks of edge-case work. Consequence: we pin the version and isolate it behind `TorrentEngine`.
- **D-2 В· 2026-10-13 В· Tauri v2, not Electron** вЂ” system WebView2, small installer, low RAM. Consequence: Windows first; Linux/macOS later without a rewrite.
- **D-3 В· 2026-10-13 В· Embed librqbit in the Tauri process; IPC, not its HTTP API** вЂ” no extra port, no auth surface, lower latency. The HTTP API stays an option for a future remote UI.
- **D-4 В· 2026-10-13 В· Svelte 5 + TS, plain CSS tokens** вЂ” smallest runtime, fine-grained updates suit a live list. No component kit, to keep the look ours and the bundle small. (Reversible before M1 ends.)
- **D-5 В· 2026-10-13 В· Queue, ratio goals, schedule built by us in `core`** вЂ” not provided by the engine; driven via pause/resume through the trait.
- **D-6 В· 2026-10-13 В· No Python anywhere** вЂ” project owner rule. Tooling is Rust/TS/PowerShell.
- **D-7 В· 2026-10-13 В· Working name "Drift"** вЂ” placeholder until the owner picks one.

- **D-8 В· 2026-10-14 В· Search is provider-based; no bundled scrapers for third-party index sites** вЂ” owner wants search. Scrapers break whenever a site changes and carry legal/maintenance risk; Torznab is the standard way for users to plug in their own sources, and Internet Archive gives a legal built-in. Consequence: `SearchProvider` trait + registry; adding a source never edits existing code.
- **D-9 В· 2026-10-14 В· Cargo workspace: `drift-core` / `drift-server` / `src-tauri`** вЂ” headless mode needs the engine and logic without a window. Consequence: core must stay free of Tauri/HTTP deps; two composition roots.
- **D-10 В· 2026-10-14 В· Playlists are a pure function in core (`.m3u8`)** вЂ” same code for GUI and headless.
- **D-11 В· 2026-10-14 В· Torznab API keys go in Windows Credential Manager, not the settings JSON** вЂ” needs a keyring crate (justified here per CLAUDE.md rule 7).

- **D-12 В· 2026-10-14 В· Plugins are sidecar processes speaking JSON-RPC over stdio; no DLLs, no WASM, no UI plugins** вЂ” language-agnostic, crash-isolated, no extra runtime in a light app. Trade-off accepted: Windows can't strictly sandbox a child process, so permissions are consent plus signatures plus resource limits (PLUGINS.md). Supersedes the earlier "no plugin system" non-goal, which was written before search needed independently updatable sources.
- **D-13 В· 2026-10-14 В· Build search providers in-tree first (M6), extract to plugins in M7** вЂ” the plugin protocol should be shaped by two or three real providers, not guessed. Once extracted, the in-tree copies are deleted and `torznab`/`archive_org` ship bundled as first-party plugins.

- **D-14 В· 2026-10-14 В· IP filter is a built-in module (`core::ipfilter`), not a plugin, and is applied inside the engine through `set_ip_filter`** вЂ” it sits on the connection hot path and must be lock-free; parsing and fetching are pure/simple. A `blocklist` plugin kind can later feed lists into the same service. Third-party lists are untrusted: size caps, sanity limits, last-good fallback. The emule-security list is a user-enabled preset, never on by default.

- **D-15 В· 2026-10-14 В· No ratio spoofing** вЂ” the client always reports true uploaded/downloaded totals to trackers, with no fake-upload mode and no behaviour designed to avoid tracker detection. Reason: it defrauds trackers and other seeders, and it is the fastest way to get an account banned. The need behind it (poor ratio on dead torrents) is served by the ratio assistant instead.
- **D-16 В· 2026-10-14 В· Remote UI reuses the desktop front-end** вЂ” one codebase, `api` layer with two transports; no separate web app.

- **D-17 В· 2026-10-14 В· `tauri-plugin-dialog` for the folder picker** вЂ” official plugin, needed for "change download folder"; permission limited to `dialog:allow-open`. (CLAUDE.md rule 7 justification.)
- **D-18 В· 2026-10-14 В· The frontend `api` has a mock transport used outside Tauri** вЂ” lets the UI be developed and measured in a plain browser with N fake torrents (`?n=1000`), and is the seam for the remote HTTP transport (M6-09). Selected at startup by `__TAURI_INTERNALS__`.
- **D-19 В· 2026-10-14 В· Native window frame for now** *(superseded by D-40)* вЂ” the custom title bar (M3-05) risks losing Windows 11 snap layouts; do it once the app is otherwise done.

- **D-20 В· 2026-10-14 В· M2 dependencies (CLAUDE.md rule 7)** вЂ” `tauri-plugin-single-instance` (second launch forwards its arguments), `tauri-plugin-notification` (completion toast), Tauri's built-in `tray-icon` feature. All official and small. Notifications and the tray are used from Rust only, so no extra JS packages or capabilities.
- **D-21 В· 2026-10-14 В· Autostart uses the `auto-launch` crate directly, not `tauri-plugin-autostart`** вЂ” the plugin writes the machine-wide Run key whenever the process is elevated and exposes no option; a per-user setting must stay per-user (found by testing from an elevated shell). The crate is already the plugin's own dependency.
- **D-22 В· 2026-10-14 В· No in-app "register as magnet handler" button** вЂ” Windows protects the user's default-app choice and a registry write could overwrite another client's setting. The installer registers `magnet:` and `.torrent` (M3-04).
- **D-23 В· 2026-10-14 В· The backend decides whether the window is visible** вЂ” WebView2 keeps `document.hidden == false` after the window is hidden to the tray, so the loops combine the native window state with the UI's report, and a `window-shown` event makes the UI catch up when it returns.

- **D-24 В· 2026-10-14 В· `core::manager` sits between the app and the engine** вЂ” queue order, categories, tags, goals and the seeding clock are not engine concepts. The manager is the only thing the UI mutates through; it uses pure planners (`queue`, `rules`) that are unit-tested against the fake engine. The engine gains no new methods for any of it; queueing is just pause/resume. Per-torrent bookkeeping lives in `library.json`, separate from `settings.json`.
- **D-25 В· 2026-10-14 В· A torrent first seen already paused is treated as user-paused** вЂ” so adopting torrents from older versions never auto-resumes something the user stopped.

- **D-26 В· 2026-10-14 В· Play-while-downloading is a loopback HTTP range server in `drift-core`, fed by the engine's seekable `open_file`** вЂ” players need HTTP with Range requests; the engine's file stream prioritises the pieces being read. 127.0.0.1 only, random per-run token in the URL, `Host` must be loopback (DNS-rebinding guard), `GET`/`HEAD` only. The player is launched with a one-line `.m3u` holding the URL, opened with the default app for that type.
- **D-27 В· 2026-10-14 В· The fake engine mirrors the real engine's strictness** (resuming a running torrent is an error) so manager bugs of that kind fail in unit tests; found when real-app Play failed on a running torrent.

- **D-28 В· 2026-10-14 В· The VPN guard is a watchdog, not interface binding** вЂ” librqbit's bind-to-adapter returns "not supported" on Windows. The guard polls the adapter list every 2 s and pauses everything (and holds the queue and new adds) while the chosen adapter is down or unaddressed; no adapter chosen counts as unprotected. Documented in the UI as leaving a gap of up to one interval. A hard guarantee would need an engine patch (bind by source address) or firewall rules; recorded as a future option.
- **D-29 В· 2026-10-14 В· Network settings restart the engine session** вЂ” port, UPnP, DHT, proxy and the IP filter file are read when a session starts, so `set_network` rebuilds it (persistence and fast resume bring the torrents back, limits are re-applied, and a failed rebuild restores the previous session). Settings that fail to apply are rolled back so what is saved always matches what runs.
- **D-30 В· 2026-10-14 В· IP filter lists are parsed and merged by us, not by the engine** вЂ” the engine reads only `name:start-end`/gzip. We download, unzip (whitelisted entries, in memory), parse eMule/PeerGuardian/CIDR, validate, merge into one normalised file and hand that over. Plain-http lists are allowed but flagged. Not a privacy tool: it blocks connections, it doesn't hide the address.
- **D-31 В· 2026-10-14 В· The proxy mode turns off listening and DHT** вЂ” only outgoing TCP can go through SOCKS5; leaving DHT and the listener on would expose the real address around the proxy.
- **D-32 В· 2026-10-14 В· New dependencies for M5 (rule 7)** вЂ” `reqwest` (already in the tree via the engine) for list downloads, `zip` (deflate only) and `flate2` for archives, `chrono` (clock only) for local weekday and time, `windows-sys` (IpHelper) to list adapters.
- **D-33 В· 2026-10-14 В· Search sources are the user's own choice** вЂ” only Internet Archive ships on by default (public-domain and openly licensed material). Anything else comes in through Torznab, i.e. through an indexer the user runs and configures, so Drift ships no list of sites. Results from several sources merge by info-hash and show every source as a badge.
- **D-34 В· 2026-10-14 В· Search API keys are stored in `secrets.json`, write-only from the UI** вЂ” a plain file in the per-user data folder rather than Windows Credential Manager (a dependency, and nothing to share with the headless server later). Upgrade path noted in the code. Error text from providers never contains the address or key.
- **D-35 В· 2026-10-14 В· New dependencies for M6 search (rule 7)** вЂ” `quick-xml` to read Torznab feeds, `futures-util` (alloc only) for the parallel fan-out, `async-trait` for the provider trait; reqwest gains its `query` and `json` features.
- **D-36 В· 2026-10-14 В· One core, two front ends** вЂ” the loops (VPN guard, watch folder, IP-list refresh), settings application with rollback, search, add/inspect and playlists live in `drift-core` (`background`, `service`); the Tauri commands and the HTTP handlers only translate. `ApiError` and Windows adapter listing moved to core too.
- **D-37 В· 2026-10-14 В· Remote access is one bearer token, plain http, loopback by default** вЂ” 256-bit token in `server.json`, no cookies (so no cross-site request can use it), no query-string tokens. Non-loopback binds print a warning; TLS is left to a VPN or reverse proxy until there is a reason to build it in. Default port 8793 (8787 is taken on the author's machine by another service).
- **D-38 В· 2026-10-14 В· New dependencies for M6 server (rule 7)** вЂ” `axum` (HTTP + SSE), `tower-http` (static UI files), `getrandom` (token), `windows-sys` moved from the app to core (adapter list, Windows only).
- **D-39 В· 2026-10-14 В· Installer: NSIS, per-user, magnet registered only if free** вЂ” no admin prompt, nothing in HKLM. `.torrent` uses the bundler's file association; `magnet:` is written by an installer hook only when no handler exists and is removed on uninstall only if Drift wrote it, so installing never takes the link type from another client. Unsigned for now (SmartScreen will warn); signing needs a certificate.
- **D-40 В· 2026-10-14 В· Custom title bar with a window-proc subclass for snap layouts** вЂ” decorations off; Windows only shows the snap flyout when the pointer hit-tests as the maximize button, which a webview can't do, so a small subclass (`caption.rs`, windows-sys, Windows only) answers that for the rectangle the page reports. If the flyout ever misbehaves, setting `decorations` back to true restores the native frame with no other change.
- **D-41 В· 2026-10-14 В· Updates from GitHub Releases, repo made public** вЂ” the updater can't read a private repo, so `Krab1/driftbt` goes public (history checked for secrets first). A minisign key (outside the repo, no password) signs each installer; the public key is baked into the app. Update checks contact github.com once a day unless switched off in Settings; installing always asks. New dependency (rule 7): `tauri-plugin-updater`.
- **D-42 В· 2026-10-14 В· Plugins are discovered from `<data>/plugins`, enabled per id in settings, and judged by their behaviour** вЂ” a plugin is a child process speaking JSON-RPC lines (`docs/PLUGIN_PROTOCOL.md`). Calls time out (5 s), a crash restarts with a doubling delay, three failures in a row switch it off until restart, idle ones are ended after 5 min, and on Windows a Job Object caps memory at 256 MB. The environment is cleared. Results from plugins are treated as untrusted and cleaned. No new dependency beyond tokio's `process` feature and two `windows-sys` features. Permissions are shown, not enforced (PLUGINS.md). Rule 8: the `Host` type is concrete; `SearchProvider` was already the seam.
- **D-43 В· 2026-10-14 В· Peer countries from an embedded offline database, flags as SVG** вЂ” `core::geoip` unpacks DB-IP "IP to Country Lite" (CC BY 4.0; attribution in Settings в†’ General) on first use, so no lookup ever leaves the computer and an idle app pays nothing. The file is compiled by `scripts/build-geoip.mjs` into `crates/drift-core/data/country.bin` (2.2 MB gzipped, about 8 MB in memory once opened); refresh it by rerunning the script with a newer CSV. Dependency (rule 7): `flag-icons` 7.5.0 (MIT) because Windows has no flag emoji; its SVGs are loaded one by one when shown. The country sits on `PeerInfo` and is set by the engine that builds the peer list, so every front end gets it.
- **D-44 В· 2026-10-14 В· List columns are chosen per viewer** вЂ” the optional columns (Added, Finished, Uploaded, Ratio, Peers, Category, Tracker) and their order live in the browser/webview's storage, not in settings. `finished_at` is stamped only when Drift sees a torrent go from incomplete to complete, so torrents that finished earlier show "вЂ”" rather than a wrong time.
- **D-45 В· 2026-10-14 В· Recheck is a re-add that keeps the files** вЂ” librqbit hashes files only when a torrent is added, so `recheck` deletes the torrent from the session without touching files and adds it again from the stored torrent bytes (same save folder, file selection and paused state). Drift's own bookkeeping is keyed by info-hash and survives. The manually supplied peers of the first add are not kept, so a damaged torrent finds its peers again through trackers and DHT. Refused while the VPN guard is holding traffic. Verified against a real loopback seeder: a damaged file drops progress, good pieces stay, a repaired file checks out clean.
- **D-46 В· 2026-10-14 В· Move on complete is done by moving files while the torrent is out of the session** вЂ” the same delete-keep-files and re-add used for recheck, with `fsmove` between them (rename, or copy then delete across drives; nothing overwritten; rolled back on failure). It runs from the ticker in its own task so snapshots never wait on a slow copy. Torrents are only moved when Drift sees them finish, not retroactively.
- **D-47 В· 2026-10-14 В· In-app update starts the installer after Drift has exited** вЂ” the plugin's own order (start installer, then exit) left Drift alive when the installer checked for it, which stopped the update with "Failed to kill Drift" (and the installer's step that runs the old uninstaller happens before any hook of the new installer can act). The app now downloads and verifies the update, writes the installer to a temp folder and starts a detached helper that waits 3 s, force-ends Drift if it is still there, then runs the installer with `/P /R /UPDATE` (passive, restart Drift afterwards). Verified: app gone, installer ran, installed Drift came back. Installers still end a running Drift themselves for manual runs.
- **D-48 · 2026-10-14 · Errors carry their technical text behind a More details button** — ApiError and TorrentStats have an optional detail / error_detail with the raw engine or OS text; the plain sentence stays the headline (UI_SPEC copy rule) and the raw text only appears when asked for: toasts, the Add dialog and failed torrent rows each get a button that opens a dialog with the text and a Copy button. Adding a torrent also retries up to four times when saving the torrent list fails, since Windows can refuse that file swap for a moment.

- **D-49 · 2026-10-14 · A torrent with several files gets its own folder inside the save folder** — librqbit uses an explicitly given output folder as is, so Drift (which always gives one, for categories and the download folder) was unpacking a torrent's game, lib and similar folders straight into the save folder, mixing torrents together and making a second torrent with the same file names fail to add. `add` now looks the torrent up first (list-only, instant for a .torrent file) and saves into `<save folder>/<torrent name>/` when it has more than one file; single files go straight in; a magnet nobody answers yet goes in `magnet-<hash>`. `relocate` follows the same rule. Torrents added before this keep the folder they were given.

Note: rqbit already ships its own Tauri desktop app (web UI wrapped). We are not forking it; our value is a purpose-built native-feeling UI plus queue/rules/streaming UX.
- **D-50 · 2026-10-15 · The plugin registry is a minisign-signed file in the repo, and updates apply at the next start** — one `registry/index.json` signed with the app's existing update key (no second key to guard), hashes of each zip inside it. A running plugin can't be replaced on Windows, so installs are staged and swapped before anything starts; rollback reuses the same swap. New dependencies (rule 7), all already compiled for the updater: `minisign-verify` (check the signature), `sha2` (check each download), `base64` (decode key and signature).
- **D-51 · 2026-10-15 · The installer has its own name and no Restart Manager check** — tauri's NSIS template aborts with "Failed to kill Drift" whenever Windows lists something holding drift.exe and cannot shut it down; a killed Drift stays listed for a few seconds, and the cause on the user's machine was never observed. `scripts/release.ps1` now patches the rendered installer script and rebuilds it with makensis: the check is replaced by nothing (`DriftStopApp` in `installer-hooks.nsh` ends Drift, waits until Windows no longer lists drift.exe and the exe can be opened for writing), and the installer reports itself as "Drift Installer" instead of "Drift". The update copy is `Drift-Installer.exe`.
- **D-52 · 2026-10-15 · Search sources are bundled plugins, and a plugin form can have lists** — `torznab` and `archive_org` are one 1 MB program in `crates/drift-search-plugin` (no `drift-core`, so no engine) that ships inside the installer and is copied into the plugins folder at start; the in-app providers are deleted. Several Torznab indexers needed a `list` field type (rows with their own secrets, `list.row.field` keys) and a `source` label per result row, and plugins can now say why a search failed (`error.data.reason`) so the app keeps its own plain wording. Trade-off accepted: one status per plugin instead of one per indexer. No new dependency in the app; the plugin crate reuses reqwest, quick-xml, chrono and serde, which the app already compiled.

- **D-53 · 2026-10-15 · Post-processing plugins get a completion event and can only move or notify** — the host (`background::postprocess`, shared by the desktop app and the headless server) tells enabled `postprocess` plugins when a torrent finishes and runs the actions they return. `move` goes through `Manager::relocate`, so seeding continues; `rename` is deliberately absent (it would corrupt what the torrent seeds). No new dependency; a failure is a toast and never touches seeding.
- **D-54 · 2026-10-15 · Theme packs are validated JSON of colours, kept in settings** — no file format beyond a small JSON object, no plugin folder, no code. Only the colour tokens can be set, so a pack can't change layout or load anything. A low-contrast pack is allowed with a warning rather than refused, because the user chose it. No new dependency.
- **D-55 · 2026-10-15 · Files you skip stay sparse (a thin wrapper around librqbit's file storage)** — a file you leave unticked still gets the few hundred KB that share a download piece with a file you did pick, and the engine then gives it its full length. librqbit meant to mark such files sparse on Windows but its call to the OS leaves out a required argument, so a skipped 641 MB file took 641 MB. `sparse_storage` in `engine/rqbit.rs` marks a file sparse just before its first write when it is still empty (picked files get their full length up front and are untouched), and `fsmove.rs` copies sparse files without filling the holes on a cross-drive move. The wrapper answers the session saver's "is this the filesystem storage" question with yes, because it is the same files in the same layout; without that the saver refuses it. Dependency: `anyhow`, only for the signatures of librqbit's storage trait (librqbit already brings it in); `windows-sys` gets three more feature flags.
- **D-56 · 2026-10-15 · A settings file that is busy is not a missing one** — `load()` used to treat any read error as "first run", and startup then filled in the Windows Downloads folder and saved, replacing the user's file with defaults. It now retries for a second, and only a genuinely missing file is written at startup.
- **D-57 · 2026-10-15 · The status-bar speed limit opens a small menu, and Settings is the gear at the top left** — the old status-bar toggle sent you to Settings when no value was set, and the Settings button on the right was easy to miss. The speed-limit button now opens a popover (Off, three presets that spell out what they set, Custom with two fields), and the gear replaces the logo mark next to the search box. No new setting: the menu writes the same `limits_enabled` and limit values the Speed tab does.
- **D-58 · 2026-10-15 · Speed limits are one Download line and one Upload line, and a torrent can have its own** — the status-bar menu has a separate choice per direction (Unlimited, common speeds, Custom). A torrent's own limit is stored in `library.json` (`limit_down_kib`, `limit_up_kib`) and applied through the engine trait's `set_torrent_limits`. librqbit applies a torrent's limit and the session limit one after the other, so the slower of the two wins and the overall limit can never be exceeded; a test proves it (a 20 MB/s torrent limit under a 128 KB/s overall limit takes as long as 128 KB/s alone). librqbit only reads a torrent's limit when the torrent is added, so changing it re-adds the torrent the way recheck does (same files and state, peers found again), and the manager sets the limits again on every tick, which is a no-op unless the engine was restarted.
- **D-59 · 2026-10-15 · Changing a torrent's limit keeps its record of finished pieces** — re-adding a torrent to change its limit deletes it from the engine, and deleting also deletes librqbit's record of which pieces are done (`<hash>.bitv` in the session folder), so the whole torrent would be hashed again, and again at every launch for limited torrents. `set_torrent_limits` copies that record and puts it back before adding (a test fails without it). It also takes the session-rebuild lock, so a change can never land on a session that is being replaced. Known cost: a re-added torrent starts its uploaded-bytes counter from zero, so a ratio goal restarts too, as it already does after any restart of the app.
- **D-60 · 2026-10-16 · Downloaded files are not held open for writing (Drift has its own file storage, replacing D-55's wrapper)** — librqbit 9.0.1 opens every file read+write when a torrent starts and never lets go, not when it finishes and not when it is paused. Windows will not start a program that something holds open for writing (`CreateProcess` fails with "being used by another process", and Explorer shows no icon), so a downloaded game's `.exe` did not run while Drift was open. `sparse_storage` in `engine/rqbit.rs` is now a full `TorrentStorage`: reads use a read-only handle kept open (harmless for running a file), a write handle is opened on demand and closed two seconds after the last write, and `take()` (pausing) closes everything. Files are created when first written or sized instead of all at once, so a skipped file that is never touched has no empty file on disk. The folder is found through the session on first use. A test opens each downloaded file the way Windows does when it launches one (share-read only) while seeding, paused and resumed. Skipped files are still marked sparse (D-55) when first written while empty.
  Kept from librqbit: the first time a torrent is added, its own storage runs once to refuse files that are already in the folder (handles closed again at once), but not when the same torrent restarts after an error. A storage that has been paused (`take()`) refuses further writes, so a late write cannot bring back a deleted or moved file. Waiting for the session at start has no short timeout, because a read that fails there looks like damaged data and discards the record of finished pieces.
- **D-61 · 2026-10-16 · Adding a torrent doesn't wait for it: a pending add is a library entry plus an in-memory row** — `Manager::add_later` (used by the app and the HTTP server) returns the id at once, writes the torrent's library entry with a `pending` record (the magnet or address, chosen files, paused) and shows a row built from the `dn=` name; a background task then does the ordinary `add`, and a failure leaves the row as an error to remove. The id of a magnet is its info-hash, so category, tags and queue position are set immediately and nothing changes id; an address gets a temporary `address-…` id that is replaced by the real one. A `.torrent` file is read on the spot (it is local), so a bad file is refused at once. Pause and resume on a waiting row are remembered and applied when the torrent exists; remove stops the add. The engine's `add` fetches a magnet's details once and adds from the fetched torrent (it used to fetch them twice). Unticking a file with data in the detail panel asks first; deleting goes through `Manager::set_files(…, delete_unchecked)`, which deletes the files and then rechecks the torrent, because the first and last download piece of a file are shared with its neighbours.
- **D-62 · 2026-10-16 · A file you didn't pick is not in your folder: its few shared bytes live in one hidden file** — D-55 kept such a file sparse, but Explorer then showed it at full size ("641 MB, 0.5 MB on disk"), which looked like a download. The few hundred KB it shares with a picked neighbour (a download piece can't be checked without them) now go into `.drift-skipped-<hash>` in the torrent's folder: an append-only log of (file, offset, bytes) records with an in-memory map, hidden, a few hundred KB at most per skipped file. The real file is created only when you pick it, and the stored bytes are written into it then. Reads of a skipped file's unstored parts give zeros, because librqbit abandons a whole file after one failed read, and a missing part should only fail the piece that needs it. The first time a torrent is opened, empty files made by librqbit's own overwrite check for skipped files are removed, and sparse stubs from older versions are converted (non-zero bytes into the log, stub deleted). Removing the torrent with its files deletes the hidden file; moving the torrent moves it. The log is never compacted (only a rewritten range is dead space). Guards that came out of review: only the first and last piece of a skipped file ever go to the log (so streaming one doesn't copy it), zeros are only answered while the torrent is being checked (a running torrent reading something it doesn't have is an error), the picked set is kept in memory and updated when you change picks (never asked of the torrent from inside a read, which could deadlock with its own lock), one log object per torrent, every record carries a signature and is checked against the file lengths, a log that can't be opened is an error rather than empty, and only a sparse file that holds no more than two pieces is converted as an old stub.
- **D-63 · 2026-10-16 · `tracker-sim` is a separate simulator plugin crate, announce-only first** — `crates/drift-tracker-sim-plugin` (binary `tracker-sim`, not bundled; installed with `scripts/install-tracker-sim.ps1`) announces to the trackers of the torrents the user switches on, as persistent identities with jittered schedules and rate-engine counters, to test a tracker you operate. No core change. Real peer traffic, proxies and DHT/PEX are designed in `docs/plugins/tracker-sim-design.md` and left for later phases. No new dependency in the workspace (reqwest, tokio, chrono, serde were already compiled); randomness is a 20-line splitmix generator, because behaviour must be reproducible from a stored seed and `rand` would add a crate for it. Enum settings are `text` fields because the form has no dropdown.
- **D-64 · 2026-10-16 · `tracker-sim` phases 2-4: a local loopback swarm, per-identity proxies, no public-network DHT/PEX/LSD** — `loopback_pair` runs the peer wire protocol over real TCP on 127.0.0.1 between a plugin's own peers, with synthetic content checked against its own generator, so counters are bytes that really moved. Proxies are per identity and saved with it; a peer without a proxy in `per_peer` mode doesn't run rather than leak the real address. DHT/PEX/LSD are not built: they only matter on a real swarm the plugin never joins, and would publish info hashes to the public DHT or the LAN.
